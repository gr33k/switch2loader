## Safe-stop boundary, 2026-10-23

Current USB waiting state is before any HID transfer or exploit trigger. Disconnecting the cable and exiting NXHID with **+** leaves no ns2jb run to clean up. This is different from a failed exploit run. In pinned ns2jb, `REMOVE` corrupts SmileBASIC process memory before later version/CRC validation. The pipeline can commit scratch changes to mounted save/tmp filesystems, and after native promotion it may abandon rather than retire the acquisition on failure. `fs-execute.cjs` restores its instruction patch only when the write is known to have changed bytes and no native request remains pending. A native worker timeout leaves `pending=true`; the stage runner sends SIGTERM at its deadline and SIGKILL five seconds later. An external service restart could also interrupt cleanup. Therefore neither “stop” nor “reboot” is a universally proven safe recovery operation after an in-flight failure. The upstream README says to restart after failure, but it does not prove all persistent side effects were removed. No physical exploit attempt is authorized by this test status; the FS start API remains locked.

In libnx's `result.h`, `0xFA01` decodes to module 1 (`Kernel`) and description 125 (`InvalidState`); the error does not identify which USB operation failed. Thus the newer cable passed some USB data, but stable keyboard readiness is not established. No sender was started and Switch 2 was disconnected. The original Switch's built-in **Copy to a Computer via USB Connection** isolation test has not yet been performed. Apple documents that new hubs may require accessory approval, and Nintendo documents the built-in screenshot connection; do not assume the Mac can complete that mode's file-transfer protocol merely from enumeration. No Mac boot security setting, Switch save, or exploit state changed.

## FS demo safety hold, 2026-10-23

The owner linked [a first-person brick report](https://x.com/KomodoSSBM/status/2113532446847414660) and asked for a cautious path. Its public post says a Switch 2 brick was caught on video; the exact commands, persistence mechanism, and recovery outcome have not been independently established. Do not attribute the brick to a particular save restoration step without primary evidence. The pinned [ns2jb README](https://gitlab.com/pepsipu/ns2jb/-/blob/95f5525089273c5fce0b95047f3600f8442e96ae/README.md) says to restart after a failed run and to enter `REMOVE` once per application process; its opening note says the author has not read the distributed package. Source inspection shows mounted `save` and `tmp` filesystems are cloned for scratch work, prior scratch removal uses a filesystem Commit, and the FS demo patches a native instruction block before attempting restoration. This is more than a RAM-only or cable-tethered operation. Successful host tests do not bound the device brick risk.

At this revision `fsDemoSafetyHold` is hardcoded true. The site labels the demo paused, disables Start even with all checklist boxes complete, and removes executable console commands from its guide. The LAN companion rejects `/api/start` with HTTP 423 before origin, readiness, or host spawning checks. Local `npm test` passed three Node tests, including a real server request proving `423`, `idle`, stage `0`, and an empty command; three Python FTP tests passed. `node --check` passed for server and browser script, and `git diff --check` passed. No exploit host, FTP upload, NXHID sender, or Switch 2 action occurred during this check. The hold may be lifted only after a documented failure analysis and physical recovery evidence; changing the UI alone must never re-enable the API. Rollback for a code error is a targeted Git revert and restart of only the companion; while risk remains unresolved, stop the companion rather than reverting to an executable build.
