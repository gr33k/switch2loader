## Safe-stop boundary, 2026-10-23

Current USB waiting state is before any HID transfer or exploit trigger. Disconnecting the cable and exiting NXHID with **+** leaves no ns2jb run to clean up. This is different from a failed exploit run. In pinned ns2jb, `REMOVE` corrupts SmileBASIC process memory before later version/CRC validation. The pipeline can commit scratch changes to mounted save/tmp filesystems, and after native promotion it may abandon rather than retire the acquisition on failure. `fs-execute.cjs` restores its instruction patch only when the write is known to have changed bytes and no native request remains pending. A native worker timeout leaves `pending=true`; the stage runner sends SIGTERM at its deadline and SIGKILL five seconds later. An external service restart could also interrupt cleanup. Therefore neither “stop” nor “reboot” is a universally proven safe recovery operation after an in-flight failure. The upstream README says to restart after failure, but it does not prove all persistent side effects were removed. No physical exploit attempt is authorized by this test status; the FS start API remains locked.
