## NXHID transfer preparation, 2026-10-23

The local wizard's step 2 now explains the official NXHID package, full application mode, direct USB-C data connection, a one-line keyboard probe, and saving the pinned bootstrap as `NS2`. The local companion accepts only a private original-Switch IPv4 address, only the `probe` or pinned `bootstrap` transfer, and only an exact same-origin request with its local header. It verifies the pinned ns2jb commit and `bootstrap.bas` hash plus the NXHID sender and `.nro` hashes before sending, and refuses concurrent transfer/host sessions. The public static page does not expose a remote transfer API. Sender process completion means bytes were sent; the user must inspect the Switch 2 editor before the save gate is checked.

The optional FTP install step accepts only the verified `.nro`, a private original-Switch IP, a bounded port, and transient credentials. It looks only for the Switch SD card's `/switch` folder, uploads to a temporary name, reads the bytes back, then renames into `/switch/nxhid/nxhid.nro`; a different previous NRO is preserved with a timestamped backup. The original Switch must already be running an FTP server. On this owner's FTP server, the missing NRO returned FTP `450 No such file or directory` as a temporary-class response, not `550`. The initial upload attempt created the empty `/switch/nxhid` folder but wrote no file. The uploader now recognizes this exact missing-file response and its cleanup tolerates the same response when the temporary name has already been renamed. Four focused FTP tests pass, including the `450` case. A subsequent upload succeeded; independent FTP readback matched the pinned NRO hash and showed only `nxhid.nro` in the new folder. To roll back the device-side preparation, remove only `/switch/nxhid/nxhid.nro` and the empty `/switch/nxhid` directory via FTP after NXHID is closed; there was no prior file to restore. Do not touch unrelated SD-card files.

The remaining physical gates are NXHID launch, USB keyboard enumeration, and a harmless one-line probe; the bootstrap and FS demo remain unexecuted. If transfer misbehaves, use **B** in NXHID to disconnect and release keys, then exit with **+**. Keep the program editor contents for diagnosis instead of blindly rerunning. To roll back the wrapper change, revert the uploader commit and restart only its companion service if the deployed copy was updated; delete only the ignored `upstream/nxhid-release` directory after confirming no sender is active. Other services, Switch saves, and Mac boot security are outside this change.

## FS demo safety hold, 2026-10-23

The owner linked [a first-person brick report](https://x.com/KomodoSSBM/status/2113532446847414660) and asked for a cautious path. Its public post says a Switch 2 brick was caught on video; the exact commands, persistence mechanism, and recovery outcome have not been independently established. Do not attribute the brick to a particular save restoration step without primary evidence. The pinned [ns2jb README](https://gitlab.com/pepsipu/ns2jb/-/blob/95f5525089273c5fce0b95047f3600f8442e96ae/README.md) says to restart after a failed run and to enter `REMOVE` once per application process; its opening note says the author has not read the distributed package. Source inspection shows mounted `save` and `tmp` filesystems are cloned for scratch work, prior scratch removal uses a filesystem Commit, and the FS demo patches a native instruction block before attempting restoration. This is more than a RAM-only or cable-tethered operation. Successful host tests do not bound the device brick risk.

At this revision `fsDemoSafetyHold` is hardcoded true. The site labels the demo paused, disables Start even with all checklist boxes complete, and removes executable console commands from its guide. The LAN companion rejects `/api/start` with HTTP 423 before origin, readiness, or host spawning checks. Local `npm test` passed three Node tests, including a real server request proving `423`, `idle`, stage `0`, and an empty command; three Python FTP tests passed. `node --check` passed for server and browser script, and `git diff --check` passed. No exploit host, FTP upload, NXHID sender, or Switch 2 action occurred during this check. The hold may be lifted only after a documented failure analysis and physical recovery evidence; changing the UI alone must never re-enable the API. Rollback for a code error is a targeted Git revert and restart of only the companion; while risk remains unresolved, stop the companion rather than reverting to an executable build.
